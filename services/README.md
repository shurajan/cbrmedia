# services

Бэкенд cbrmedia для Ubuntu: четыре независимые systemd-службы над общей служебной папкой `~/.cbr`.
Каждую можно включать и выключать отдельно — остальные продолжают работать.

| Служба | Что делает | Пишет | Читает |
|---|---|---|---|
| [recorder](recorder/README.md) | опрашивает status API и записывает стримы | `recordings/`, состояние и события в базе | список слежения |
| [tbot](tbot/README.md) | Telegram: `/add`, `/del`, `/list`, уведомления о выключенных и удалённых пользователях | список слежения | состояние, события |
| [api](api/README.md) | HTTP API плеера: видео, список слежения, события | список слежения, удаляет видео | `media/`, база |
| [converter](converter/README.md) | `recordings/` → HLS в `media/` (ffmpeg) + `meta.json` | `media/` | `recordings/` |

Каждая служба раз в несколько секунд отмечается в базе (heartbeat: имя, версия, время); `GET /health` у api показывает,
кто запущен и какой версии. Без живого recorder api и tbot на добавление пользователя отвечают сразу, не ожидая проверки.

`core/` — общая библиотека: служебная папка, база, конфиги, запуск, метаданные видео (`meta.json`).

## Как службы связаны

Напрямую — никак. Общение идёт через общую базу `~/.cbr/data/cbr.db` (SQLite, WAL) и через файлы:

```
 tbot / api / (WhatsApp…) ──пишут──▶ watchlist ──читает раз в 3 с──▶ recorder ──▶ recordings/ ──▶ converter ──▶ media/ ──▶ api
                ▲                                                       │
                └──────────── events, watch_state ◀──────── пишет ──────┘
```

- **watchlist** — кого записывать. Интерфейсы не отдают команд recorder: они меняют список, а recorder сам
  сверяется с ним. Новый интерфейс (например, WhatsApp) — это новая служба, которая пишет в ту же таблицу.
- **watch_state** — что recorder делает сейчас (статус комнаты, идёт ли запись).
- **events** — журнал событий. Каждый читатель хранит свою позицию в `cursors`, поэтому выключенный бот
  после запуска дошлёт пропущенное.
- **services** — heartbeat служб: кто запущен, какой версии, когда отмечался. Корректно остановленная служба
  удаляет свою строку.

База — SQLite в режиме WAL, её одновременно открывают все службы. Это работает только на локальном диске одной
машины: служебная папка на сетевом диске (NFS, SMB) ломает блокировки WAL и может повредить базу. Службы одной версии
обновляются вместе (`install.sh` без аргументов): бинарник старее схемы базы не стартует.

## Служебная папка `~/.cbr`

Переопределяется переменной `CBR_HOME`. Службы сами создают недостающие папки и работают из `~/.cbr`,
поэтому неважно, откуда запущен бинарник. Пути описаны в одном месте: `core/home`.

```
~/.cbr/
├── bin/                 # recorder, tbot, api, converter
├── config/
│   ├── recorder.json    # base_url, подключения status_api и cdn
│   ├── tbot.json        # bot_token, allowed_user_id, подключение telegram (chmod 600)
│   ├── api.json         # addr (по умолчанию :8000), status_base_url, подключение status_api — всё необязательно
│   └── auth.json        # хэш пароля плеера (api hash-password)
├── data/
│   ├── cbr.db           # общая база (SQLite)
│   └── converter.lock
├── recordings/          # сырые записи (*.ts / *.mp4, part-файлы); failed/ — не удалось преобразовать
├── media/               # HLS-библиотека плеера (<папка>/playlist.m3u8 + meta.json)
└── logs/                # <служба>.log, ротация через logrotate
```

## Настройка конфигов

Конфиг службы пишет её же бинарник — подкоманда `config` есть у `recorder`, `tbot` и `api`:

```bash
~/.cbr/bin/recorder config             # спросит все параметры; Enter оставляет значение в [скобках]
~/.cbr/bin/recorder config --base-url https://example.com/api/streamcontext \
  --status-api http://127.0.0.1:8080 --cdn direct      # без вопросов: задать переданное, остальное не трогать
~/.cbr/bin/recorder config --help      # справка: параметры, формат значений, примеры
```

| Служба | Флаги (ключи конфига те же, через `_`) |
|---|---|
| `recorder config` | `--base-url <url>` (обязателен), `--status-api`, `--cdn` |
| `tbot config` | `--bot-token <токен>`, `--allowed-user-id <id>` (оба обязательны), `--telegram` |
| `api config` | `--addr <host:port>`, `--status-base-url <url>`, `--status-api` |

- Без флагов команда спрашивает все параметры по очереди: Enter оставляет текущее значение, `-` очищает
  необязательный параметр, неверный ответ переспрашивается. С хотя бы одним флагом вопросов нет.
- Подключение (`--status-api`, `--cdn`, `--telegram`) — одно значение: `direct`, адрес HTTP-прокси
  (`http://127.0.0.1:8080`) или имя сетевого интерфейса (`eth0`, `wg0`); `proxy` / `interface` — снова включить
  адрес прокси / интерфейс, сохранённый в файле. `direct` сохранённое не стирает. Интерфейс должен быть в системе:
  команда выполняется на той же машине, что и служба, и при опечатке перечисляет имеющиеся.
- Пустое значение флага (`--status-base-url ""`) очищает необязательный параметр.
- Конфиг проверяется теми же правилами, что при старте службы; неверный не записывается. Файл пишется атомарно
  с правами `0600`. Значение токена на экран не выводится (но вводится открыто).
- Существующий файл читается без проверки, так что командой можно исправить конфиг, с которым служба не стартует.
  Непустой ключ `"proxy"` прежней нотации переносится в секцию службы (`status_api` / `telegram`), если прокси в ней
  ещё не задан. Ключи, которых служба не знает, в новый файл не попадают.
- После изменения службу нужно перезапустить (`sudo systemctl restart cbr-<служба>`).
- Файл можно править и вручную — шаблоны `<служба>/config.example.json`. Пароль плеера задаётся отдельно:
  `api hash-password`. Справка и вопросы команды — на английском, как остальной вывод бинарников.
- Общий код (разбор флагов, диалог, справка, запись) — `core/configcli`; состав параметров — `CLI()` в
  `internal/config` службы.

## Подключения и прокси

У каждого внешнего адресата в конфиге своя секция одной и той же формы (Go `core/config.Connection`):

```json
"status_api": {
  "connection": "proxy",
  "proxy": "http://127.0.0.1:8080",
  "interface": ""
},
"cdn": {
  "connection": "interface",
  "proxy": "",
  "interface": "wg0"
}
```

| Адресат | Секция | Файл |
|---|---|---|
| Telegram API | `telegram` | `tbot.json` |
| status API — опрос статуса и ссылки на стрим | `status_api` | `recorder.json` |
| CDN — плейлисты, ключи, сегменты | `cdn` | `recorder.json` |
| status API — ссылка для живого просмотра | `status_api` | `api.json` |

- `connection` — способ подключения:
  - `direct` (по умолчанию, в том числе без секции) — как решит операционная система: маршрут по умолчанию;
  - `proxy` — через HTTP-прокси из `proxy`;
  - `interface` — через сетевой интерфейс из `interface` (`eth0`, `wg0`…).
- `proxy` — адрес HTTP-прокси; обязателен при `"connection": "proxy"`.
- `interface` — имя сетевого интерфейса; обязательно при `"connection": "interface"`.
- Действует только выбранное в `connection`; прокси и интерфейс вместе не работают. Невыбранные значения можно
  оставить в секции и переключать только `connection`.
- Общих настроек нет: секции друг на друга не влияют. Переменные окружения `HTTP(S)_PROXY` не действуют.
- Подключение через интерфейс (`core/netdial`) — привязка сокета: `SO_BINDTODEVICE` в Linux, `IP_BOUND_IF` в macOS;
  на других системах — ошибка при старте. В Linux обычному пользователю это разрешено с ядра 5.7, на более старых
  нужен `CAP_NET_RAW`. Если интерфейса нет при старте, служба не запускается (systemd перезапустит её через 5 с);
  если он пропал позже, запросы через него завершаются ошибкой — на маршрут по умолчанию служба не переходит.
  Имена хостов разрешает системный резолвер, DNS-запросы идут обычным маршрутом. На Linux не проверено.
- Ошибка в секции останавливает службу при старте. Так же — непустой ключ `"proxy"` верхнего уровня (нотация до
  1.4.1): адрес нужно перенести в секцию, которую называет текст ошибки, — вручную или командой `<служба> config`.
- Выбранное подключение служба пишет в лог при старте.

## Разработка

Требуется **Go 1.26+** (патч-версия закреплена в `go.mod`, Go скачает её сам). Каждая служба — отдельный
Go-модуль; `core` подключается через `replace cbr/core => ../core`.

```bash
./dev.sh                    # собрать и запустить весь back-end локально (macOS/Linux)
./dev.sh recorder api       # только эти службы
make test                   # тесты всех модулей
make check                  # vet + golangci-lint + test + govulncheck по всем модулям
```

`dev.sh` работает со служебной папкой `~/cbr-dev`, чтобы не трогать `~/.cbr` (другую задаёт `CBR_HOME`).
Перед первым запуском:

1. `./dev.sh` — соберёт бинарники в `~/cbr-dev/bin/` и подскажет, каких конфигов не хватает;
2. задать конфиги (`CBR_HOME=~/cbr-dev ~/cbr-dev/bin/recorder config`, то же для `tbot`) и пароль плеера:
   `CBR_HOME=~/cbr-dev ~/cbr-dev/bin/api hash-password --password <пароль>`;
3. `./dev.sh` ещё раз — службы запустятся в этом терминале, вывод каждой с префиксом `[служба]`,
   копия в `~/cbr-dev/logs/`. Ctrl+C останавливает все.

Если на сервере уже работает бот с тем же токеном, локальный tbot будет получать `409 Conflict`: заведите
тестового бота или запускайте без него (`./dev.sh recorder api converter`). converter нужен ffmpeg
(`brew install ffmpeg`); локально он проверяет записи каждую минуту (`CONVERT_INTERVAL`). Подробные логи — `DEBUG=1 ./dev.sh`.
Одну службу без сборки можно запустить через `go run`: `CBR_HOME=~/cbr-dev make -C api run`.

В папке модуля доступны те же цели (`make help`). Общий конфиг линтера — `.golangci.yml`, общие цели — `common.mk`.

## Деплой на Ubuntu

```bash
services/deploy/install.sh                 # все службы
services/deploy/install.sh recorder tbot   # только эти
sudo systemctl disable --now cbr-tbot      # выключить службу
tail -f ~/.cbr/logs/recorder.log
```

Скрипт делает `git pull`, собирает бинарники в `~/.cbr/bin/`, перезаписывает unit-файлы `cbr-<служба>.service`
и запускает службы. Если для службы нет конфига, ставит только бинарник и подсказывает команду `<служба> config`;
после неё скрипт запускается ещё раз. Ротация логов
(`/etc/logrotate.d/cbrmedia`): раз в сутки (`maxsize 100M` проверяется только при этом запуске — файл больше
100 МБ ротируется на ближайшем, а не сразу), 14 архивов, `copytruncate`.
Прежние монолитные службы `cbrservice` и `cbrconvert` скрипт останавливает и удаляет.
